## 1. 项目背景与商业论证

### 1.1 现状与痛点（待业务方补充实测数字）

货架陈列巡检当前依赖人工：督导或门店人员到店拍照、人工核对货架上的商品是否符合陈列计划、是否缺货、是否串位。该流程存在三类典型问题：

1. **人力成本高、覆盖有限** —— 人均单次巡店耗时 ___ 分钟，每人每日可覆盖 ___ 家门店，导致巡检频次和覆盖率受限。
2. **一致性与准确性不稳定** —— 人工核对受经验、疲劳、主观判断影响，错判/漏判率约 ___%，且难以追溯。
3. **不可审计** —— 巡检结果缺少结构化留痕，事后无法复核、无法用于陈列合规考核与供应链补货决策。

> ⚠️ 以上空白处（___）必须在立项评审前由业务方填入真实测量值。**没有基线数字，"人工审核时间下降 30%/50%"这一成功指标无法验收，项目也无法计算投资回报。** 若暂无精确数据，至少用一个典型门店做一次计时与抽样测算。

### 1.2 项目目标

建立一套由 **Label Studio、本地视觉模型、多模态 SKU 知识库和 YOLO 检测** 组成的、**可审计的人机协同识别闭环**：系统自动检测商品区域并给出 SKU 裁决建议，人工只做预标注结果的审核与纠错；所有预测、审核、模型/知识/提示词变更全程版本化、可追溯。

**首期（MVP）聚焦**：单一货架巡检场景，30～50 个高相似 SKU（必须包含同品牌不同规格、口味、新旧包装），完成技术验证并达到受控试点门槛。

### 1.3 投资回报框架（ROI）

立项评审需回答"值不值得自研"。用下表做粗算（业务方填数）：

| 项目 | 估算口径 | 数值 |
|---|---|---|
| 当前年人工巡检/审核成本 | 人数 × 人均成本 × 投入比例 | ￥___/年 |
| 当前错判导致的业务损失 | 缺货损失 + 陈列不合规损失 | ￥___/年 |
| 系统建设一次性投入 | 人力 + 硬件/GPU + 标注 | ￥___ |
| 系统年运维投入 | 人力 + 算力 + 存储 | ￥___/年 |
| 预计年节省 | （人工成本 + 损失）× 可替代比例 | ￥___/年 |
| **预计回本周期** | 一次性投入 ÷（年节省 − 年运维） | ___ 个月 |

决策规则建议：**回本周期 > 24 个月，或可替代比例 < 30%，应重新评估范围或改为采购商业方案（见 §3）。**

## 2. 项目范围

### 2.1 首期范围内（In Scope）

- 单一货架/陈列巡检场景，现场拍摄照片的识别。
- 30～50 个高相似 SKU 的检测 + SKU 级识别。
- 三种非强制出口：**未知 SKU / 图片不可判定 / 候选冲突**，一律转人工，不得强制匹配。
- 两阶段识别：开放词汇/YOLO 检测商品区域 → 条码 + OCR + 视觉向量检索 + 硬冲突规则 + 本地视觉大模型（VLM）裁决。
- Label Studio 预标注展示 + 人工审核；追加式人工反馈进入数据版本。
- 模型、提示词、知识库、数据集全程版本化；变更经固定金标准集 + 影子运行后方可发布。
- 固定金标准评测、发布门、影子运行、一键回滚、只读审计接口。

### 2.2 首期范围外（Out of Scope，明确排除）

- 多场景、多门店类型的泛化（第二场景需走范围闸门，见 §2.3）。
- SKU 数量超过 50 个的批量扩展。
- 视频流 / 实时摄像头识别。
- 陈列合规（planogram）的**空间位置**判定（首期只识别"是什么 SKU"，不判定"摆在对不对的位置"）。
- 自动补货 / 自动下单等业务系统联动。
- 训练或推理使用云端闭源大模型 API（首期坚持本地可审计）。

### 2.3 范围闸门（Scope Gate）—— 防止"通用"二字失控

项目名含"通用 SKU"，但首期刻意收窄。**扩展必须满足以下前置，缺一不可，由业务负责人 + 项目负责人共同批准：**

| 扩展动作 | 前置条件 |
|---|---|
| 增加第二批 SKU（50 → N） | 首期门槛全部通过；知识库更新流程已跑通并有审计记录；新增 SKU 不影响现有分组指标 |
| 增加第二业务场景 | 首期已进入受控试点且连续两轮评测达标；新场景完成独立的范围冻结与金标准构建 |
| 增加空间/陈列合规判定 | 识别 Top-1 准确率稳定达标；单独立项评审（属新功能，非识别能力延伸） |
| 接入业务系统联动 | 错误自动通过率连续低于试点门槛；具备回滚与熔断机制 |

## 3. 自研 vs 采购论证（Build vs Buy）

立项必须明确回答"为什么不直接买商业货架识别 API"。采用自研需至少满足以下之一，并在评审会记录结论：

| 自研理由（需勾选并说明） | 是否成立 |
|---|---|
| 数据敏感/合规，图像不得出内网，必须本地部署 | ☐ |
| 商业方案无法识别本业务的高相似 SKU（同品牌多规格/新旧包装） | ☐ |
| 商业方案不可审计，无法满足留痕/合规/可追溯要求 | ☐ |
| 长期规模下自研总成本显著低于按量付费 | ☐ |
| 需要与内部知识库、审核流程深度集成 | ☐ |

> 若以上均不成立，应**暂停自研，转为商业方案 POC 对比**。这是本章程设置的一道硬闸门。

## 4. 成功标准与阶段门槛

成功标准沿用《技术实施计划》的量化门槛，**不可降级**。摘要如下（详见 `configs/evaluation/gates.yaml`）：

| 指标 | 技术验证门槛 | 试点门槛 |
|---|---:|---:|
| 商品框召回率 | ≥95% | ≥97% |
| SKU Top-5 召回率 | ≥95% | ≥97% |
| SKU Top-1 准确率 | ≥85% | ≥90% |
| 高置信自动通过错误率 | ≤2% | ≤1% |
| 未知 SKU 错误接纳率 | ≤3% | ≤1% |
| 人工平均审核时间下降 | ≥30% | ≥50% |
| 预测/审核/版本审计覆盖率 | 100% | 100% |

**一票否决项**：错误自动通过率超标，无论整体准确率多高，不得发布。

**业务侧成功标准（需基线支撑）**：
- 单次巡店人工核对时间较基线下降 ≥30%（技术验证）/ ≥50%（试点）。
- 巡检覆盖率或频次较现状提升 ___（业务方设定）。

## 5. 里程碑与阶段

沿用 M0–M4，**小团队修订工期见《实施 WBS》§5**。此处为标准定义：

| 里程碑 | 交付物 | 通过/停止条件 |
|---|---|---|
| **M0 范围冻结** | 场景定义、SKU 清单、标注规范、金标准协议、许可证结论、本章程签字 | 停止：无法取得 ≥30 高相似 SKU 及现场图；或无法确定人工终审责任人 |
| **M1 技术验证** | 知识库、三条识别基线、500 张金标准评测报告 | 停止：Top-5 < 95% 或未知错误接纳率 > 3% → 先修数据与召回，不扩建平台 |
| **M2 MVP 闭环** | Label Studio 预标注、追加反馈、数据版本、YOLO 训练、发布门 | 停止：审计覆盖率 < 100% 或错误自动通过率 > 2% |
| **M3 受控试点** | 真实业务影子运行、人工效率报告、回滚演练、知识库更新流程 | 停止：连续两轮未改善人工时间；或关键 SKU 分组指标持续退化 |
| **M4 生产扩展** | 规模化运行、运营体系 | 进入：试点门槛全通过 + 业务方接受剩余人工量 + 许可证与硬件成本获批 |

## 6. 角色与职责（RACI）

> R = 负责执行，A = 最终问责（唯一），C = 需咨询，I = 需知会。小团队下一人可能身兼多角色，但 **A（问责）在同一事项上必须唯一且明确**。

| 角色 | 核心责任 | 首期承担人 |
|---|---|---|
| 项目负责人 / 业务 Owner（A） | 冻结范围、确认验收门槛、批准上线、范围闸门审批 | 待定 |
| 商品知识负责人 | SKU 主数据、条码、规格、包装版本、冲突规则 | 待定 |
| CV 工程师 | 检测、检索、YOLO 训练、指标分析 | 待定（⚠️ 瓶颈，见下） |
| 后端 / MLOps 工程师 | API、事件、数据版本、模型注册、发布与回滚 | 待定 |
| 标注负责人 | 标注规范、审核一致性、金标准维护 | 待定 |
| 安全 / 法务 | 数据权限、许可证、保留与审计要求 | 待定（可兼职/外部） |

**小团队资源风险提示**（详见风险登记册 R-RES）：
- CV 工程师与 MLOps 工程师是技术瓶颈。若由 1 人兼任，M1/M2 工期需串行并显著拉长。
- 标注是劳动密集环节，"已有大量图片"仍需人工确认/纠错成金标准，需评估可投入的标注工时或外包。
- 建议在立项时即明确：哪些角色内部承担、哪些需外部支援/外包，并写入预算。

## 7. 治理与决策机制

### 7.1 决策层级

| 决策类型 | 决策人 | 机制 |
|---|---|---|
| 范围、门槛、治理机制变更 | 业务负责人 + 项目负责人 | 变更控制流程（书面申请 → 影响评估 → 联合批准 → 更新章程） |
| 阶段门槛是否通过（能否进入下一阶段） | 项目负责人，依据评测报告 | 评测报告 + 一票否决项检查 |
| 模型/知识/提示词发布 | 发布审批人（ release-policy 定义） | 金标准评测 + 影子运行 + 审批留痕 |
| 日常技术方案取舍 | 技术负责人（CV/后端） | 团队内评审，记录于文档 |

### 7.2 评审节奏（建议）

- **阶段门评审**：每个里程碑结束时，依据门槛出具通过/停止/整改结论。
- **双周迭代评审**：小团队以两周为一个迭代，同步进度、风险、门槛接近度。
- **风险评审**：每迭代过一遍风险登记册 Top 5。

### 7.3 一票否决与停止纪律

- 任何硬门槛失败即阻止发布，当前生产模型保持不变。
- 达到里程碑"停止条件"时，**默认动作是停止/整改，而非继续**；继续需业务负责人书面批准并承担说明责任。

## 8. 关键假设与约束

### 假设（若不成立需重估）
- A1：已有图片数据质量足以支撑金标准构建（待数据专项计划核实）。
- A2：能确定唯一的人工终审责任人，且其有时间投入审核。
- A3：本地具备运行 Qwen2.5-VL 与 YOLO 训练的 GPU 算力（需硬件预算获批）。
- A4：30～50 个首期 SKU 的条码、规格、包装版本等主数据可齐全录入。

### 约束
- C1：数据与模型本地部署，图像不出内网（合规）。
- C2：小团队人力，任务以串行为主。
- C3：所有密钥仅经环境变量注入，不落库、不进代码仓库。
- C4：金标准集独立冻结，不参与训练/调参/阈值选择。
