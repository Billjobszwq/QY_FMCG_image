# 架构决策与原理（ADR）

> 本文件讲**为什么**这样设计；模块/目录/数据布局见 `structure.md`，怎么跑见 `runbook.md`，怎么装见 `setup.md`。

## ADR-01 三阶段解耦：大模型当老师，YOLO 当学生

- **决策**：多模态大模型只用于**自动标注**（产出训练标签）；YOLO 是被训出的**检测-识别**模型，上识别热路径。
- **理由**：大模型准但慢/贵，不适合每张图实时跑；YOLO 快但需要数据。让大模型把"知识"蒸馏进 YOLO 的训练集，热路径只跑 YOLO，是成本/延迟/质量的最优分工。
- **代价**：标注阶段需人工门兜底（见 ADR-02）；YOLO 质量受限于自动标签质量。
- **何时重审**：若大模型推理成本/延迟降到可接受，可让大模型重回热路径做硬样例复核。

## ADR-02 人工门：自动只提案，张张过人工

- **决策**：自动产出**只是提案**（`proposals/`）；只有人工 `approved` 的照片才进训练源（`approved/`）；低置信进复核队列、**不训练**。
- **理由**：自动标签必有错，直接训练会"教错"并自我强化。人工门是数据可用的命门。
- **代价**：吞吐量受限于人工；靠"模型提案好→人工一键确认"提速。
- **何时重审**：当大模型在"人工确认集"上的错误率稳定低于门槛，可**经你显式同意**后对高置信样本抽样免审（trust-but-verify），默认不开。

## ADR-03 native 优先，Docker 可选

- **决策**：默认全本机原生运行；Postgres/MinIO/Redis/Label Studio 容器为可选。
- **理由**：① 国内直连 Docker Hub 常 TLS 超时，docker 成了阻塞项而非助力；② 每个组件都有原生等价物且多数已建好；③ 先把项目跑通优先于容器化。
- **代价**：多节点/协作/生产需另做容器化或原生部署（PG `brew`、LS `pip`、对象存储用阿里 OSS）。
- **何时重审**：进入多机/团队/生产时，按 `setup.md` 第 6/7 节启用。

## ADR-04 检索只召回，裁决 = 硬过滤 + VLM 终审

- **决策**：向量检索只负责**召回 top-K**；最终 SKU 由"解析属性硬过滤 + VLM 在候选内终审"决定，**不取 embedding top1**。
- **理由**：实测 KB 端纯向量 top1 在同瓶型不同糖度/容量上不可靠（如"茉莉乌龙 无糖"top1 误为"微甜"）。而真正区分高相似 SKU 的是标签文字（糖度/容量/口味），硬过滤+VLM 正好用上。
- **代价**：每张多一次 VLM 调用；OCR 读不全时硬过滤降级（此时降置信、转复核）。
- **何时重审**：补 KB 端属性化索引/重排后，可复测 top1 是否已够好。

## ADR-05 追加式 + 原始资产只读

- **决策**：`annotation/auto_label/review_event` 在 DB 层禁 update/delete；原始资产（参考图、xlsx、源图缓存）在代码层 `assert_writable` 拦为只读；人工动作只追加 `review_events.jsonl`。
- **理由**：数据可信与可审计。错了用"新事件"纠错，不抹历史；原始数据永不污染。
- **代价**：存储只增；靠内容哈希去重控制。

## ADR-06 本地 SQLite 仓库先行，PG/MinIO 同构后切

- **决策**：元数据用 SQLite，schema 与 Postgres 同构（`migrations/001_schema.sql`）；向量在 numpy 文件；blob 在本地内容寻址目录。
- **理由**：零依赖今天能跑；单写场景（批处理/训练）SQLite 足够；同构 schema 让"切 PG"是迁移而非重写。
- **代价**：SQLite 单写，**多 worker 并发写百万级**会成瓶颈。
- **何时重审**：上异步多 worker 时切原生 PG（`SKIP LOCKED` 当队列）+ OSS。

## ADR-07 标注双模式：B 种子驱动 / A 从零

- **决策**：模式 B 用它模给的 `(x,y,name)` 当种子→画框+打 SKU+**复核纠错**；模式 A 无种子→OCR 锚定位+识别。
- **理由**：现成数据多带弱标签，B 能用且能反向挖掘它模错标；A 覆盖裸图。
- **代价**：模式 B 的框由种子外扩（启发式，非精确框）；模式 A 的 OCR 锚 LOC 坐标缩放**未校准**。
- **何时重审**：需要精确框时引入开放词汇检测器或微调检测器出框。

## ADR-08 级联架构：YOLO 冻结画框 + 分类器动态精识别

- **决策**：识别热路径采用**级联两段**——YOLO（冻结于 sku_v4 best.pt，mAP50≈0.69）只负责**检测画框**；轻量分类器（ResNet18/EfficientNet-B0，224x224 抠图）作为第二道闸门做**细粒度 SKU 精识别**。分类器置信度 <0.6 时回退 YOLO 预测或标记人工复核。
- **理由**：YOLO 单网络在 208 类细粒度分类上遇到架构天花板（mAP50 稳定 0.68~0.69，继续死磕投入产出比极低）；但其召回率高（0.69）、画框准。把「画框」与「细粒度分类」解耦，用专门的分类网络攻克 YOLO 的分类短板，目标将业务 SKU 准确率提升至 95%+。
- **可持续闭环（关键）**：
  - **YOLO 永久冻结**：日常迭代不修改、不重训 YOLO best.pt，它只做画框器。
  - **分类器动态维护**：发现新的易混淆 SKU 组合时，只需收集困难 SKU 抠图补充到 `crop_dataset/<sku_id>/`。
  - **快速增量微调**：对分类器执行低温微调（`src/cascade/finetune.py`：冻结骨干、仅训分类头、lr=1e-4、15-20 轮），每次仅需 10~20 分钟算力。
- **代价**：每框多一次分类器前向（轻量，MPS 上毫秒级）；需维护 crop_dataset 与分类器版本。
- **何时重审**：若轻量分类器仍无法区分某些极相似 SKU，可升级骨干（EfficientNet-B0→B2）或引入对比学习/难例挖掘。

## 已知缺陷与缓解

| 缺陷 | 缓解 | 状态 |
|---|---|---|
| KB 端检索 top1 在糖度/容量弱 | 裁决走硬过滤+VLM（ADR-04） | 已兜底，KB 回归待补 |
| `recognize.detect_bottles` 直传 bytes 给 ultralytics | 识别评测已用 numpy 绕开；服务路径待改 numpy | 待修 |
| smoke 训练仅 1 张 approved | 仅作链路证明；真训练需更多人工数据 | 设计如此 |
| 金标仅 9 张，指标仅供参考 | 扩金标；指标加置信区间 | 待办 |
| 模式 A 的 OCR LOC 缩放未校准 | 模式 B 不依赖；模式 A 用前校准 | 待办 |

## 规模化路径（百万级，未实现）

异步队列（Redis 或 PG `SKIP LOCKED`）+ 每图幂等检查点 + omlx 调用批处理/缓存 + 提示合并降本 + blob 迁 OSS + 元数据迁 PG + 分布式训练。当前同步/后台脚本仅适合千张级验证。
